06「错误即操作手册」机制

27 个错误 subtype 集中在注册表里，调用点只给 subtype + 动态数据。这样修一次文案，所有地方同步。

四个语义字段
  • action_required：self（自己能解决）/ user（必须问人）/ none（无能为力）
  • dead_end：这条路没有替代走法，不是可重试的失败
  • must_end_turn：立即结束本轮，别试别的命令
  • forbidden：列出「看起来能绕过但其实没用」的做法
死路状态机
撞 dead_end
   ↓ setBlock(blocked.json)
任何相关命令 → { blocked:true }
   ↓ 用户补齐条件
fastgpt model id 成功
   ↓ clearBlock()
恢复正常（24h 自动失效兜底）
信息分层（v0.2.0 定下的规则）： 决定「下一步动作」→ hint（必须到命令级）； 「这个错怎么改」→ details.issues[].code + fix 标记； 「禁止做什么」→ forbidden + SKILL 红线； 「为什么 / 怎么排查」→ README + tests。只写在文档里 = 大概率没被读。

校验规则清单（16 个 issue code，按可修复性分两类）

类别fixcode
图结构autohandle_legacy_port · handle_target · handle_format
图结构manualhandle_branch（分支 key 不在分支列表）
引用语义autoref_selected_type（值是引用但 selectedType 不是 reference）
引用语义manualvar_undefined · ref_node · ref_output
渲染契约autobare_variable_ref · addinputparam_null · ifelse_value_type · ifelse_valuetype_enum
渲染契约manualbare_variable_undefined · canedit_const_value
平台约束manualmodelId 非 ObjectId（warning）· answer 重复引用 · 孤立节点（warning）
为什么必须有 normalize 这一步（而不是「更严格的报错」）

导出文件是跨版本产物：handle 按输出 key 命名、变量裸写 {{key}}、canEdit 输入存常量、ifElse 条件值存 boolean —— 这些在新版本里语义都变了，但服务端运行时仍然兼容。 所以旧文件「能跑，长得不对」。纯报错只会逼人绕过校验；规范化器才是正解：能修的修，修不掉的（需要人决定怎么改内容）才报 error。

这也是 v0.2.0 把校验器从黑名单（只认构造器产出形态）改成白名单 + 平台语义（VARIABLE_NODE_ID 是合法伪节点、ifElse 分支与 catch 边都合法）的原因。

09本地状态与文件

~/.fastgpt/config.json
服务地址。优先级：FASTGPT_BASE 环境变量 > 配置文件。600 权限。
~/.fastgpt/cookies.json
会话 token（fastgpt_token）。600 权限。auth logout 删此文件。
~/.fastgpt/blocked.json
死路阻断状态。model id 成功后自动清除，24h 兜底失效。
./.fastgpt/apikey
OpenAPI key，apikey create 时写入当前目录。项目 .gitignore 要盖住。

环境变量：FASTGPT_HOME（多实例隔离）· FASTGPT_BASE · FASTGPT_APP_KEY · CHROME_PATH（扫码登录）

10质量与边界

140 项离线断言（不触网）
  • 节点构造器：16 个存在性 + 关键字段
  • 校验规则：本轮 6 类坑逐条回归（全局变量放行、未定义报错、裸变量、canEdit 常量、null、ifElse 值）
  • 规范化：handle / 裸变量 / null 三连修复
  • 错误契约：category → 退出码映射、Notice 结构
  • 协作者权限：完整列表语义 / POST 方法 / idKey
刻意不做的事
  • 不做「离线也能 build」：避免用占位 modelId 产出「看起来成功」的假象
  • 不内置 CDP / 浏览器检测：破坏零依赖，且属验收手段而非平台契约
  • 不自动改内容级问题：canedit_const_value 要人决定内联还是保留
  • 不猜地址/凭证：缺 FASTGPT_BASE 就报 not_configured 并给 4 个预设
已知局限（诚实记录）： 校验器仍是「重写的一套规则」，没有直接吃平台 schema —— 平台再新增机制（新节点类型、新输入渲染类型）时，还是会有一次「误判 → 放行」的补丁周期。 长期方向是启动时拉 feConfigs + 节点模板，用真实 schema 校验 handle 与 inputs。
